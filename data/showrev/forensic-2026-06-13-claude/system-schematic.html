What we are trying to protect

Two operator objectives sit above this whole system:

  1. Verified data. Every fact in an email body must come from a source we can defend if a recipient asks "how do you know that?"
  2. Verified email addresses. Every send goes to a real person at a real address we have evidence is theirs.

Every red and yellow item below puts one of those two objectives at risk.

A. The active pipeline (CSV in → email out)

Today the system runs TWO pipelines in parallel on the same prospects, by design — operator compares output. The v2 path (substrate-tier-first) is shown below. The v1 path (run-pipeline.ts) is similar but lacks tier discipline.

STEP 4 BROKEN — this is the headline gap

Evidence orchestrator — "what do we know about this company?"

evidence-tiering/orchestrator.ts + substrate-query.ts + apollo-client.ts
Pulls company evidence from substrate, Apollo, industry associations, FCC BDC — in parallel. Then deterministically computes a tier per claim (USE_DIRECTLY or USE_TO_SHAPE) based on which kind of source it came from.
In
company name + ICP type
Out
TieredDossier with claims grouped by category and tier
Root cause of the substrate-quality crisis. Tier is computed from source_kind (how it was harvested), not from the URL domain. A ZoomInfo URL pulled via a dated web search gets source_kind = web_research_dated, which the tier table maps to USE_DIRECTLY — the highest trust. 12 ZoomInfo/LeadIQ/RocketReach rows confirmed in production across 3 prospects.
The fix already exists as code but is stranded. verify-facts.ts has the URL-domain classifier (knows ZoomInfo is prohibited). It is imported by the deprecated v1 pipeline only. The v2 path never calls it. Wiring it in is ~5–6 hours of work.

STEP 5 WORKING

Composer — write the email

If the dossier has 3+ usable claims, runs "specific mode" — references USE_DIRECTLY claims as approximations ("north of 1,500 miles") rather than exact numbers. Otherwise runs "generalized mode" — industry framing only, no company-specific claims. Best-of-N retry with mechanical regex checks (banned phrases, AI-tell patterns, company-name lock, paragraph and word count, reading age, citation coverage).
In
TieredDossier + persona + AE identity
Out
ComposedEmail with sentence-level claim_ids attribution
Carry-forward risk from Step 4. The composer is doing the right thing — but if the dossier it receives carries USE_DIRECTLY claims sourced from ZoomInfo, the composer treats them as authoritative. Garbage in, garbage out. Fixing Step 4 fixes this.

STEP 6 WORKING

Tiered judge — three layers of QA

tiered-judge.ts (851 lines)
T1 mechanical regex (instant, free). T2 Tim-style edit-pattern check (~3s, free). T3 Gemini quality + always-on hallucination check (~10s, $0.005/email). Hallucination check fires on every prospect. If it fails, the email is flagged for human review with the specific unsupported claims named.
In

Out
verdict: ship / retry / flag / flag-hallucination
Observation, not a code bug. judge_feedback_loop_attempts = 0 on every row queried. The feedback loop is built (up to 2 recompose iterations with offending claim_ids excluded) but isn't firing on current rows. May indicate the pipeline isn't re-running through judge for older rows.

D. The risk zones, ranked

Risk 1 — Substrate ingest has no URL-domain check

Objective at risk: verified data.

What happens. When the substrate ingest writes a row to sr_company_evidence, it sets source_kind from how it was harvested ("dated web research"), not from the URL domain. A ZoomInfo URL becomes web_research_dated → USE_DIRECTLY → eligible to be quoted in an email body.

Evidence in production. 12 PROHIBITED-domain rows across 3 prospects (CNE / PC Telcom / United Tel Supply). Confirmed by Supabase queries last night.

Fix path. Wire verify-facts.ts URL-domain classifier into the substrate-write step. ~5–6 hours per the second-pass plan A FINAL.

Risk 2 — Email-verification fields are null on most rows

Objective at risk: verified email addresses.

What happens. The email-finder waterfall computes a confidence color and verification report — but the writes to email_confidence, verification_report, mv_quality, email_verified, email_verification_status are null on most rows queried. "MV-verified" claims cannot be backed by DB state.

Fix path. Audit the write side of email-finder/orchestrator.ts → supabase-adapter.ts. Identify why fields are dropped. Backfill once fixed.

Risk 3 — ICP gate has deliberate inclusivity bias

Objective at risk: list quality (a precursor to data quality).

What happens. icp-gate.ts tells Haiku: "if uncertain, classify as fiber_operator with low confidence. False negatives are 10x worse than false positives." 36 of 36 sampled rows passed.

Trade-off. This was an explicit choice — better to capture too many than miss real ICPs. But "ICP pass" downstream gets interpreted as "ICP-verified." That's not what the column means.

Fix path. Either tighten Haiku confidence threshold, or rename column to icp_candidate and add a separate icp_verified column. Operator decision.

Risk 4 — Tim approval doesn't reset when email confidence flips

Objective at risk: don't ship to a bad address.

What happens. Tim reviews craft. Later pipeline re-runs may flip email confidence from green to red. Tim's approval stays. One prospect was queued for send Tim-approved + red.

Fix path. Add reset trigger: any email-confidence flip from non-red to red clears the Tim-approval flag and requires re-review.

Risk 5 — Ghost / deprecated code increases human error rate

Objective at risk: future-pipeline integrity (not data integrity directly).

What happens. Three deprecated pipelines (pipeline.ts → premium-pipeline.ts → run-pipeline.ts) plus composer.ts and a duplicate microsite-composer.ts are still on disk. Refutation is built and tested but explicitly not wired. New work risks editing the wrong file.

Fix path. Delete deprecated pipelines after a freeze window. Wire refutation OR archive it explicitly.

E. What's working — don't touch

  • Tiered judge cascade — three layers (regex / Tim-style / Gemini) plus always-on hallucination check is rigorous and well-implemented.
  • Composer-constraints (861 lines) — banned phrases, AI-tell hardening (DL-199 PNAS/VERMILLION), Flesch-Kincaid reading age, citation coverage, best-of-N retry.
  • Evidence orchestrator phase pattern (pull → gap-fill → tier+emit) — clean separation, parallel fetches, second-best query loop.
  • Email finder waterfall (12 sibling files in email-finder/) — domain resolver / pattern detector / peer pattern / SMTP / MV / Apollo fallback / tactic eval. Solid.
  • RLS hardening — anon key locked to live microsites + page-view inserts. Service role for code.
  • CSV column-shift bug fix — parseCsvLine handles quoted commas in company names (caught 50 of 204 affected rows on 2026-06-11).
  • Apollo credit tracker — prevents credit blowout on long runs.
  • Send confidence v1.0 — explicitly labeled "uncalibrated" so it doesn't get confused with calibrated.
  • Pre-load verify gate — SPF/DKIM/DMARC + HS auth + dedup + bounce history audit.
  • Two-pipeline-in-parallel architecture — lets the operator compare v1 and v2 output on the same cohort. Intentional, not chaos.
