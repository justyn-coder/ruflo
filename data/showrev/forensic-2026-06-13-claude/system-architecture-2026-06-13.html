ShowRev System Architecture

How a prospect goes from a name on a CSV to an email landing in their inbox.

2026-06-13 · Inorsa Fiber Connect 2026 cold-prospecting pipeline

Eight stages, top to bottom. Each one either learns something true about the prospect, makes a decision, or hands off to the next stage. Anything broken right now is shown in red below the diagram. The companion Database Architecture map lays out every table this system reads and writes.

The eight stages, in plain English

1Substrate ingest

This stage pulls verified facts about each prospect company into a database we can trust when it's time to write the email. There are two ways in: manual capture (Nick or operator shares a fact, Claude writes it as a row) and web research (we pull from Apollo, FCC, trade publications, public filings). A domain-trust classifier sits at the write boundary and refuses prohibited sources like ZoomInfo.

Reads from: Apollo, FCC BDC, web sources, Nick DMs. Writes to: sr_company_evidence and sr_brain_substrate.
Broken right now: The domain-trust classifier exists in the code but isn't wired up. 21 prohibited-domain rows are sitting in the high-trust tier today. Plan F3 wires it and backfills 1,522 existing rows.
2Prospect intake

Read the cohort CSV (210 rows for P2), decide whether each prospect fits Inorsa's ideal customer profile (fiber operator, A&E firm, or adjacent services), and find a verified email address. The email finder tries five methods in order — domain resolver, pattern detector, SMTP probe, MillionVerifier, Apollo — and stops at the first verified hit. Result is a confidence color: green, yellow, or red.

Writes to: sr_prospects.
Gate: If the email score is zero, the prospect is hard-blocked from ever being sent. If the color is red, they are held for review.
3Compose

The evidence orchestrator pulls every row we have on this company and tiers them by trust. If we have three or more strong claims, the specific composer writes a cited, company-specific body. Otherwise the generalized composer writes industry-framed copy with no specifics. Both composers use Nick's voice and Inorsa's canonical framing through prompt templates.

After the body is drafted, mechanical constraints check it: banned phrases, AI tells, Tim's kill-list, hallucinations, readability. If anything fails, the composer retries up to four times with the violations as hints.

Reads from: sr_company_evidence, sr_brain_substrate.
Gate (sprint-week add): Plan F1 adds Nick's five Inorsa-validates phrases to the kill-list. Hard-blocked at compose time. Test replays the five historical hallucination emails — expect five-of-five blocks.
Broken right now: Nick's kill-list canon isn't in the regex array. Soft enforcement through prompt templates holds for the moment but is one bad edit away from drift.
4Judge

Three judges run in order on every composed body. Tier 1 is mechanical regex, instant. Tier 2 scores craft and voice in Tim's style. Tier 3 is Gemini-powered quality scoring with an always-on hallucination check. The verdict is one of: ship, retry, flag for quality review, or flag for hallucination.

Then send-confidence combines three axes — ICP fit, email verification quality, substrate richness — into a composite score. If email score is zero, this hard-overrides to "cannot send."

Writes to: sr_engine_output (judge verdict and confidence fields).
5Persist and measure

One row per prospect per touch gets saved: the email body, the dossier, the microsite content. Everything starts as draft — nothing is recipient-visible yet.

This stage is also where observability lives. Today the audit-trail tables are essentially empty — we have been shipping output for weeks with almost no telemetry. The fix-sprint routes Claude Code's native session-correlated telemetry into the audit tables.

Writes to: sr_engine_output, sr_dossiers, sr_microsites, sr_pipeline_runs, sr_emails.
Broken right now: The audit-trail tables are empty in production. sr_pipeline_runs has zero rows ever. sr_emails has zero rows ever. The fix-sprint addresses this with five connected items.
6Operator gate

Two things happen before any send. First, eleven automated checks run: existing-contact lookup, email authentication, do-not-contact lists, dedup against prior cohorts, bounce history. Any one failure halts the prospect.

Second, the operator reviews each prospect in the /ops Mission Control portal and clicks Approve + Go Live. That single click flips the microsite to live, marks the prospect as ready-to-send, and writes an audit record. Per-prospect approval is the default; a bulk "Approve all passing" option exists when the operator wants it.

Writes to: sr_dnc_log (on failure), sr_microsites, sr_prospects, sr_review_actions.
Gate: No HubSpot load fires for any prospect where the operator hasn't approved or where no microsite is live. This is the hard human-in-the-loop checkpoint.
7HubSpot load and send

The loader upserts the contact into HubSpot in a single call (plan F7 fix — was two calls before). Every API hit gets logged with rate-limit headers so we can spot throttling early.

Then there are two paths to enrollment. The default is manual — the AE bulk-enrolls contacts from a HubSpot list using the UI. POST-PORTAL v6 ratified this over the API path because it eliminates silent-skip and sender-disconnect failure modes. The parallel test this week is the AE-proxy API path, where we'd enroll programmatically on the AE's behalf. If it passes by Sunday afternoon and the operator green-lights it, the smoke fires via API.

Writes to: sr_prospects (HubSpot ID), sr_hs_api_calls.
8Watch and learn

After the send, the watcher polls HubSpot for engagement signals: opens, clicks, replies, bounces. Tight cadence for the first fifteen minutes (every 30-60 seconds), then back off to every five minutes.

A bounce monitor watches the rolling last 20-40 sends. If the hard-bounce rate crosses 5%, it halts new enrollments. If it stays above, it pauses the sequence.

Inside Claude Code sessions, a Stop-hook reads judge verdicts and feeds calibration notes back to the next turn — a small in-session learning loop. It only fires when the signal is strong (5+ verdicts, large success-rate shift); otherwise it returns nothing.

Writes to: sr_outcomes, sr_bounce_events.

What's broken right now

1 · P1 microsites are draft-only in production. The 45 P1 booth-visitor contacts who received emails last week click their microsite link and hit nothing. Plan W1 restores from backup and flips to live (~1 hour).
2 · Tim's review is being misread by downstream code. Tim reviews craft and voice only — he does not see substrate, he does not verify claims. But the column his approval lives in (composition_reviewed_by) gets read by downstream gates as "approved for send." Plan F6 renames the column and adds a separate facts-reviewed field plus an SQL trigger that auto-resets craft approval if confidence flips to red.
3 · Inorsa-validates kill-list is not in the regex array. Nick's five forbidden phrasings are protected by prompt templates only — one bad edit and they could ship. Plan F1 adds the five regex entries (20 minutes).
4 · URL-domain trust classifier is unwired. The code exists but isn't called. 21 prohibited-domain rows are in the high-trust tier today. Plan F3 wires it, backfills 1,522 existing rows, and quarantines (does not delete) the prohibited ones for the audit trail.
5 · The brain (distilled signals) is mostly empty. Five of ten brain tables have zero rows — market signals, bellwethers, patterns. The periodic LLM-distillation pass that fills these is in the REBUILD bucket, not this sprint.
