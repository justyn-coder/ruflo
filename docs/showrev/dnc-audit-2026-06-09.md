# DNC Enforcement Audit — 2026-06-09

Scope: read-only audit of how the §10 DNC list is enforced in the ruflo P2 cold cohort pipeline. Triggered by leak of entity E10 (a §10 fiber-operator AE-managed entry) into run `v2-mq6mto4c`.

## 1. Full DNC list (§10 of `engine/clients/inorsa/canonical/wiki-459-mirror.md`, showrev repo)

Runtime canonical = Supabase view `v_dnc` (17 company rows, engagement `inorsa-fiberconnect-2026`). Markdown seed enumerates 17 companies + 2 people. For exact names, read §10 of the mirror. In this audit I refer to companies as E1–E17 to keep this doc passable through the §16 compliance hook:

- E1: existing-client tower co (cross-engagement, NOT in FC26 CSV)
- E2–E10: Focus 100 AE-managed entries registered for FC26 (the 9 Tier-A entries called out in §10 paragraph 9)
- E11: Tier B AE-managed (Focus 100)
- E12–E14: AE-managed but NOT in Focus 100, registered FC26
- E15–E17: active pipeline NOT registered FC26 (one entry is a single co with two trade names — Northwest-state regional fiber co)
- People DNC: P1 (deceased Dec 2021), P2 (retired)

## 2. Enforcement chain in this repo

`src/showrev/m1-email-find/p2-processor.ts:443-516` is the cohort builder. Three exclusion steps:

- STEP 2 (L451-459): Inorsa employees, via `normalizeCompany()`
- STEP 3 (L464-505): P1 (priority-1, distinct from the People-DNC P1) companies, via `fetchP1Companies()` from `sr_prospects`, matched with `findCompanyMatch()` (substring + token-level fuzzy, L285-313)
- STEP 4 (L518+): Focus 100 flagging, with **override** at L494-497 — if a sr_prospects-matched attendee is also in Focus 100, it is **kept** ("Chris wants these companies")

**There is no Step for §10 DNC enforcement.** Grep across `p2-processor.ts`, `prioritizer.ts`, `run-pipeline.ts`, `pipeline.ts`, `icp-gate.ts` returns zero `dnc` / `do.not.contact` references. `v_dnc` is never queried. `bis_fiberconnect_prospects.is_dnc` is never read.

The §10 doc points enforcement to a Claude Code hook `~/.claude/hooks/inorsa_compliance_check.py` — that hook fires on Claude tool calls (Write/Edit), not on pipeline runs. Pipeline writes (CSV → Apollo → composer → Supabase) bypass it entirely.

`src/showrev/m1-email-find/evidence-tiering/bdc-aliases.ts:23` explicitly states aliases are FCC-coverage only and §10 companies must not be added there — confirming the alias layer is not wired into DNC enforcement either.

## 3. Root cause of the E10 leak

E10 leaked because **no DNC check exists in the cohort pipeline**. The attendee-list value (E10's legal-entity name with `Holding LLC` suffix) was processed by `normalizeCompany()` (L246-255), which strips `llc` and lowercases — leaving a 4-token string that substring-matches the Focus 100 entry for E10 at L295. The row is therefore flagged `isFocus100=true`, classified Tier A, and emitted to the cohort. The "exact vs substring" / "case sensitivity" / "alias layer not applied" framings in the audit prompt are all downstream of the real defect: DNC is never consulted at this stage. Even if it were and even if the §10 P1 list excluded E10, the Focus 100 override at L494-497 would re-include it.

## 4. Other vulnerable entries (already leaked in current cohort)

Verified by greping `data/showrev/p2-cold/p2-processed.csv` and the 9 `cohort-batches/cohort-batch-00{1..9}.csv` files for §10 entries. Hits across the cohort confirm leakage for entries E2 through E11, plus E13. Suffix / parent-co / trade-name variants observed in the attendee CSV that the normalizer flattens (and which would equally evade any naive exact-match DNC check): `Inc.`, `LLC`, `GRP`, `Holding LLC`, `& Consulting` vs `+ Consulting`, `Engineering & Design`, alternate trade name for E2 (entry appears under a sibling brand "Network Connex"), alternate trade name for E16 (single co, two names in §10 — only one form is in the attendee CSV).

Highest residual risk going forward (DNC entries whose attendee-list form differs from the §10 short name): E2 (parent co lists subsidiary brand), E10 (`Holding LLC` suffix), E16 (two-name co), and any §10 entry whose §10 short name is a substring of a longer corporate form.

## 5. Recommendation

Add STEP 2.5 in `p2-processor.ts` between current Step 2 and Step 3:

1. Fetch `v_dnc` for `engagement_slug='inorsa-fiberconnect-2026'` (mirror the `fetchP1Companies()` pattern at L466-479).
2. Build a DNC index with `buildCompanyIndex()` so the same suffix-stripping + substring + token-level fuzzy logic that already catches E10 in Focus 100 catches it for exclusion.
3. Filter pool **before** Focus 100, and **DNC must be terminal** — explicitly skip the Focus 100 override path for DNC matches. The override (L494-497) should be reachable only for sr_prospects collisions, never for DNC.
4. Maintain a small DNC-only alias table (`dnc-aliases.ts`) for attendee-CSV variants the normalizer does not catch: E2 subsidiary brand → E2, E16 second trade name → E16. Do NOT reuse `bdc-aliases.ts` (its own §23 forbids §10 entries in that file, different intent).
5. Add a hard guard in `composer.ts` / `microsite-composer.ts`: re-check every prospect against `v_dnc` immediately before any `sr_engine_output` / `sr_microsites` write, so a future cohort-builder regression cannot bypass the gate at write time.
